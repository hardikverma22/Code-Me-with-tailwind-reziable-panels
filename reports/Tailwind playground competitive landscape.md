# Pitch the sandbox and forks, not sharing

Others have built most of the visible surface. **Tailwind Play** is the official, Tailwind-only playground and has offered account-less snapshot sharing since its 2020 launch ([Source](https://tailwindcss.com/blog/introducing-tailwind-play)). **LiveCodes** is the closest open-source product shape, with **90+ languages**, embeds and self-hosting ([Source](https://github.com/live-codes/livecodes)). Sandpack, react-live and the Vue SFC REPL cover the React and Vue niches, and CodePen, CodeSandbox and StackBlitz cover the hosted commercial tier. CodeMe therefore cannot win on "free, Tailwind, share a link," because Tailwind Play already does the share and LiveCodes already does the breadth. The edge lies in the parts the evidence can support: a documented sandbox and origin model, a fork model, a private link that needs no account, and Convex-backed short links. Four moves give the most portfolio leverage: lead with the sandbox decision, make fork-and-share the live demo, state Tailwind's limits honestly, and ship one medium feature that closes a visible gap. None of them needs the large items, such as real-time collaboration or WebContainers, to be credible.

## What portfolio reviewers reward, ranked

The ranking below is practitioner consensus, not measured preference. The notes found no primary survey of hiring managers. The most solid source is scale.jobs, which says recruiters want live demos, clear READMEs and case-study write-ups covering problem, approach and outcome ([Source](https://www.scale.jobs/blog/portfolio-content-for-tech-jobs-what-recruiters-want)). Its percentage statistics are unsourced and were excluded here.

First, reviewers want a clear problem and a working demo within the first minute. Snippet-level guides describe a fast skim of homepage, one featured project, then the code and GitHub activity, with "30 to 60 seconds" repeated across sources that cite no study ([Source](https://www.index.dev/blog/evaluate-freelance-developer-portfolio)). For CodeMe, the editor must work on the first screen. Second, reviewers reward a README that explains decisions and tradeoffs. Snippet-level guides list "what broke and how it was fixed" as a strong story and flag generic clones such as to-do apps and default templates ([Source](https://scrimba.com/articles/how-to-build-a-web-developer-portfolio-that-gets-you-hired)). CodeMe's README lists features but no decisions, so this is the cheapest gap to close.

Third, and the strongest hard evidence in the notes, is engineering judgment in the risky area. The MDN iframe reference, which was fetched, says that combining `allow-scripts` with `allow-same-origin` is strongly discouraged for same-origin content because the embedded document can remove the sandbox, and that content displayed outside the iframe escapes the sandbox ([Source](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)). A senior engineer reviewing a tool that runs arbitrary HTML and JavaScript will probe this first. Fourth, performance and mobile matter, and the notes recommend checking the animated landing page for LCP and layout shift on a phone. The Lighthouse weighting in the notes comes from a page last updated in 2019, so the current scoring should be checked before anyone quotes it. Fifth, tests, CI and accessibility matter to some reviewers, but the notes found no evidence on how much they weigh.

For presentation, the order should be landing page, then one click into a working editor, then a README that gives a 30-second scan path: what it is, one live link, one screenshot, stack, a decisions section and known tradeoffs. Index.dev suggests two to four featured projects, so CodeMe should be the single featured project rather than one of many.

## Technical differentiators by cost

Before ranking the options, one fact was checked directly in the repository. `src/components/PreviewFrame.tsx` sets `sandbox="allow-scripts allow-modals allow-forms"`, so the preview has no `allow-same-origin` and no `allow-popups`. `src/lib/buildSrcDoc.ts` forwards console output and uncaught errors to the parent window. The notes had not audited the code, so this is the first confirmed sandbox fact. The effort sizes below are judgments from the stack and the cited docs, not measured numbers.

The cheap items take about a day or two each. The first is to document the sandbox model and add a test that fails if `allow-same-origin` is ever added alongside `allow-scripts`. This is the single most credible engineering signal available, and both MDN and OWASP name the attribute as the control for untrusted content ([Source](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)). The second is a documented popup policy. Under the current attribute set, `window.open` inside a preview silently fails, and that is a usability decision worth stating. The third is a Tailwind caveat. Tailwind's own Play CDN page says it "is designed for development purposes only, and is not intended for production" ([Source](https://tailwindcss.com/docs/installation/play-cdn)), so CodeMe should state which Tailwind path user code runs through and label preview output accordingly.

The medium items take several days each. The most tractable is error-to-line mapping in the console. The preview already forwards errors, so mapping them to the user's file and line for plain HTML and JavaScript is a bounded extension that needs no full source-map toolchain, and it is visible in a live demo. OG preview images for short links would make shared links look finished on social platforms, but the approach was not verified. Export as a project, following the Vue REPL pattern, is the most obvious feature gap. A separate preview origin becomes necessary only if CodeMe ever renders user HTML outside the iframe, for example on a standalone view route. The notes do not show such a route exists, so it should be checked before anyone builds for it.

The large items take weeks. Real-time collaboration is the strongest demo candidate, and its grounding is good. Yjs is transport-agnostic, offers IndexedDB persistence and has CodeMirror bindings through `y-codemirror.next` ([Source](https://yjs.dev/)), so the editor side is tractable. The real cost is a sync server and presence UI, and it should be scoped to one room. WebContainers are a poor fit. They need cross-origin isolation across the whole page and are supported for embedding only in Chromium browsers ([Source](https://developer.stackblitz.com/platform/webcontainers/)), which conflicts with a light, account-less tool. AI generation would need a model key and a cost and abuse plan, which conflicts with the free positioning.

## Prioritized action list

1. Write a Decisions section in the README covering the sandbox attribute and why `allow-same-origin` is absent, why sharing is link-only with lz-string, why Convex is used only for short links and forks, and how a fork is modeled. This is cheap and addresses the reviewer's first question directly.
2. Add a test asserting that the preview sandbox never includes `allow-same-origin` together with `allow-scripts`. It takes under a day and turns the security claim into something verifiable.
3. Rebuild the live demo around the differentiator: create a snippet, share a private link with no account, fork it, and open the fork. Pair it with a short GIF as a README fallback. Do not describe sharing as unique, because Tailwind Play already offers account-less sharing.
4. Add the Tailwind caveat and state the Tailwind path that user code uses, so the claim matches what the preview actually does.
5. Ship one medium feature, preferably error-to-line mapping, because it extends the sandbox work and shows up in the demo. Choose OG images instead only if social sharing is the story.
6. Check the landing page's LCP and layout shift on a mobile profile against the current Lighthouse version before claiming performance.
7. Leave collaboration and WebContainers on the roadmap rather than building them. If collaboration is built, scope it to one room.

Some claims should stay out of the write-up. Do not claim that share-by-URL is unique, that CodeMe is the only free Tailwind playground, or that any feature drove stars, upvotes or interviews, because no traction data was gathered. Do not cite the CodeSandbox acquisition, pricing figures, or star counts without a date and a primary source. Avoid describing Tailwind Play's current features based on the 2020 announcement.

## How strong the evidence is

The strongest sources are the ones fetched directly: the Tailwind Play CDN docs, the StackBlitz pricing page, the MDN iframe reference, the OWASP HTML5 cheat sheet, the Yjs homepage, the WebContainers docs, the Sandpack usage docs and scale.jobs. The repository check described above is also direct. Everything else is weaker. All pricing except StackBlitz's comes from aggregators that disagree with each other, and the official CodePen, CodeSandbox, JSFiddle and JS Bin pricing pages were blocked or returned 404. Product Hunt figures come from a third-party mirror, hunted.space, and were not confirmed against Product Hunt. Star counts were observed on different dates and conflict across sources. Several claims are stale: the Tailwind Play feature list is from 2020, the Lighthouse weights are from a 2019 page, and JS Bin's last commit dates to 2021.

Some research passes were incomplete. Show HN and Reddit searches returned no usable threads, so community sentiment is missing and the UX praise and criticism that would matter for a playground are absent. Hacker News and r/ExperiencedDevs were not read successfully either. No primary study connects any portfolio feature to hiring outcomes. The notes contain no evidence on whether tests, CI or accessibility affect interviews. The ranking of reviewer priorities is therefore a reasoned judgment built on practitioner sources.

## Conclusion

The competitive landscape rewards a defensible position over a longer feature list. Tailwind Play and LiveCodes already occupy the sharing and breadth space, so CodeMe's showcase should stop competing on those axes and argue for its engineering choices instead. The notes found no competitor that publishes its sandbox and origin model in the way CodeMe could. That absence is unverified, because the search coverage was thin, but it is the cheapest gap to test, and checking it costs only a few searches on each competitor's docs.

The second implication is that the portfolio signal is the reasoning, not the feature count. A reviewer who opens the playground and then reads a short decisions section about the sandbox, the link-only share and the fork model is seeing the same product through an engineer's lens, which is what the evidence suggests reviewers are looking for. The project already has the strongest raw material for that story, so the remaining work is writing it down and making the demo show it in under a minute.
